# 12306 抢票助手

**一句话：它替你一直点「查询」，有票就喊你，并且把你送到「提交订单」前一步。**

只干这一件事，但把它做到位：不用你守着页面、不用你手忙脚乱地勾乘客，命中到提交大约 2 秒。

- 不需要装依赖（只用 Python 标准库）
- 不需要给任何账号密码
- 余票由浏览器解密，服务端不碰 12306 的加密接口
- 验证码和付款，永远留给你自己

## 它替你做什么

| 机器干 | 你干 |
|---|---|
| 每隔几秒自动查一次余票 | 在浏览器登录 12306 |
| 有票时弹窗 + 响铃 + 手机推送 | 滑一下验证码（约 2 秒） |
| 自动点「预订」，跳到订单页 | 付款（30 分钟内） |
| 自动勾乘客、选席别、把票种改成成人票 | |
| 自动点「提交订单」 | |

**它不干：** 存你的密码、破解验证码、替你付钱、绕过 12306 的风控。

为什么不做这些：验证码就是用来区分人和机器的那道闸，绕过它就不是"帮你买票"，而是"替机器买票"了。而且 12306 明确禁止第三方软件代购，替别人抢票收钱在国内属于倒卖车票。

## 三步跑起来

需要一个 Python（3.9 以上）和一个装了 Tampermonkey 的浏览器（Chrome / Edge）。

### 第 1 步：告诉它你要哪趟车

复制 `config.example.json` 成 `config.json`（第一次运行时也会自动生成），然后改 `tasks` 里的这几行：

```json
{
  "from": "广州南",
  "to": "肇庆东",
  "dates": ["2026-11-06"],
  "trains": ["D3666"],
  "seats": ["二等座"],
  "auto_jump": true,
  "auto_submit": true,
  "passengers": ["张三"]
}
```

`from` / `to` 写站名就行，拼音、缩写、电报码也都认（`广州南` / `gzn` / `IZQ` 都行）。写错了 `doctor` 会提示相近站名。

✅ **怎么算成功**：运行下面这条，能打印出你配置的车次、日期、席别，没有报错。

```bash
python run.py doctor
```

### 第 2 步：启动服务

```bash
python run.py serve
```

✅ **怎么算成功**：屏幕上打印出这一段，**这个窗口别关**（关了就停止抢票，最小化可以）：

```
==================================================================
  12306 余票监控已启动
  看板      http://127.0.0.1:8765/
  任务      1 个（启用 1）
==================================================================
```

### 第 3 步：装上浏览器脚本，打开查票页

1. 浏览器装 **Tampermonkey**（扩展商店搜"篡改猴"）
2. 打开 `userscript/12306-monitor.user.js`，全选复制
3. Tampermonkey → 管理面板 → 左上角 `+` → 编辑器里 `Ctrl+A` 删掉模板 → `Ctrl+V` 粘贴 → `Ctrl+S`
4. 打开 <https://kyfw.12306.cn/otn/leftTicket/init>，**手动登录**

✅ **怎么算成功**：页面右下角出现一个小面板，写着「查询 2026-11-06 广州南→肇庆东」。

> 两个注意：
> - 把标签页**钉住**或单独开一个窗口。Chrome 会限制后台标签的定时器，切走会变慢。
> - **只开一个**查票页。两个标签页不会更快，只会互相排队。

## 命中那一刻会发生什么

这是全流程，按时间顺序：

| 时间 | 谁做 | 发生什么 |
|---|---|---|
| 0.0 秒 | 脚本 | 发现你要的车次有票 |
| 0.1 秒 | 系统 | 桌面弹窗 + 响铃（手机推送也会发） |
| 0.2 秒 | 脚本 | 表格里那行加绿框，自动点「预订」 |
| 1.5 秒 | 脚本 | 订单页：选好席别、勾上乘客、票种改成成人票 |
| 2.0 秒 | 脚本 | 自动点「提交订单」 |
| 2~5 秒 | **你** | **滑验证码** |
| 6 秒 | 脚本 | 页面出现"未完成订单 + 30 分钟倒计时" |
| 30 分钟内 | **你** | 付款 |

**提交成功后座位就锁定了 30 分钟**，所以真正"抢"的动作就是那一下验证码，之后不用慌。

## 配置文件怎么填

### 全局设置

| 字段 | 大白话 |
|---|---|
| `server.port` | 服务端口，默认 8765。和用户脚本里的 `CFG.server` 要一致 |
| `server.token` | 可选密码。填了之后看板要用 `http://127.0.0.1:8765/?token=你的密码` 打开 |
| `poll.interval_seconds` | 每隔几秒查一次。**建议 8~15 秒**，低于 5 秒容易被弹滑块 |
| `poll.jitter_seconds` | 随机抖动，让刷新看起来没那么机械 |
| `notify.dedupe_seconds` | 同一个「车次+席别」多久内只提醒一次，默认 300 秒 |
| `poll.burst` | 开售瞬间加速窗口，见下面 |
| `poll.stop_at` | 到点自动停，形如 `2026-11-06T22:00:00` |

### 任务（tasks）

| 字段 | 大白话 |
|---|---|
| `id` | 给这个任务起个名，看板上显示 |
| `enabled` | `false` 就是先停用，不用删掉 |
| `from` / `to` | 出发站 / 到达站 |
| `dates` | 哪几天，格式 `2026-11-06`。**12306 只卖 15 天内的票** |
| `trains` | 只盯哪几趟。**空数组 `[]` = 这段所有车次**。写的顺序就是优先级 |
| `seats` | 要什么座。`二等座` / `一等座` / `无座` / `硬卧` / `软卧` 等 |
| `min_count` | 至少剩几张才算命中。`有` 这种不显示数字的状态也算满足 |
| `allow_waitlist` | 「候补」算不算命中。默认关，因为候补几乎总能点，容易误报 |
| `auto_jump` | 命中后自动点「预订」跳进订单页 |
| `auto_submit` | 再自动点一次「提交订单」，然后停住等你过验证码 |
| `passengers` | 要自动勾的乘客姓名，**必须和 12306 常用联系人里的一字不差**。空数组就是让你自己勾 |

改完配置要**重启 `serve`** 才生效。

### 预售票：用「加速窗口」

平时 8~15 秒查一次是安全的，但**开售那一秒**需要另一种节奏。这就是 `burst`：

```bash
python run.py burst --at "2026-11-05T12:59:50" --window 120 --interval 0.5
```

意思是：从 12:59:50 开始，接下来的 120 秒里，每 0.5 秒查一次（其余时间照常）。

- `--at` 填**开售时刻前 10 秒**（假设 13:00 开售就填 12:59:50）
- 关掉：`python run.py burst --off`

**为什么有用**：正常间隔下，你是"每隔 10 秒看一次"；加速窗口里你是"票一出现就在看"。开售瞬间的那 1~2 秒，这就是差别。

**为什么不能一直开着**：高频查询会触发风控，把你在最关键时刻踢下线。平时温和、关键时段全力，才是对的用法。

## 想让手机也收到提醒

默认只有电脑弹窗（本机有效）。人在外面时要靠 **Webhook**：

```json
"webhook": {
  "enabled": true,
  "kind": "bark",
  "url": "https://api.day.app/你的key",
  "headers": {}
}
```

`kind` 可选：`bark` / `serverchan` / `dingtalk` / `wecom` / `feishu` / `generic`。

用邮件也行，但要注意：`password` 填的是**邮箱授权码**，不是登录密码（QQ、163 都一样），否则会报 535 认证失败。

## 遇到这些情况怎么办

**面板没出现**
八成是这两个原因：① 你打开的不是 `https://kyfw.12306.cn/otn/leftTicket/init`（首页不生效）；② 浏览器里「允许用户脚本」这个开关没开 —— 去 `edge://extensions`（或 `chrome://extensions`）→ 篡改猴 → 详细信息 → 允许用户脚本 → 打开。

**面板显示「本地服务未连接」**
`serve` 没跑，或者端口不是 8765。先用浏览器打开 `http://127.0.0.1:8765/api/health`，能看到内容就说明服务活着。

**面板一直显示「待命中」**
这是**正常状态**——说明它在按间隔等下一轮，没有票可抢。看「已查询 N 轮」在涨，就说明在干活。

**显示「登录已过期」**
12306 把你踢下线了。可能是查得太快、或者手机 APP 同时登录了同一个账号。重新登录 → 点面板「继续」。如果反复被踢，把 `interval_seconds` 调到 10~15。

**订单页显示「常用联系人列表是空的」**
你的 12306 账号里还没加乘车人。去「我的 12306 → 常用联系人」添加（需要手机核验）。**这是所有自动抢票的前提**，没有它就只能手动输身份证。

**出票失败，提示"未完成学生优惠资质核验 [WT.9901]"**
12306 给这个乘客默认选了学生票。脚本已经把票种强制改成成人票；如果你真要买学生票，得先在 12306 APP 完成学生资质核验。

**查询几轮后弹滑块**
频率偏快了。调大 `interval_seconds`，手动滑一次，脚本会暂停等你。

**多个标签页都在跑**
引擎按「区间+日期」互斥，同一时刻只有一个标签在查。多开不会更快，只会互相排队，留一个就行。

**日志和数据库在哪**
`logs/monitor.log`、`data/monitor.db`（只有车次和告警，不含任何账号信息）。

## 它能做到什么程度

诚实版本，别抱不切实际的期待：

| 能做到 | 做不到 |
|---|---|
| 比你手点快 2~3 秒（省在"发现"和"填单"） | 保证抢到（能不能买到取决于有没有票） |
| 一直守着不用人盯 | 压过专业抢票软件（它们靠代理 IP 和打码平台） |
| 关键时段（开售瞬间）提前布阵 | 绕过验证码 |
| 页面改版时出错会明确报错 | 静默给你报错票（宁可漏报也不报错） |

三个绕不过去的物理限制：

1. **每轮 1~2 秒是下限** —— 点查询、等服务端返回、等表格渲染，这一段压不下去了
2. **高频会被风控踢登录** —— 所以默认温和，只在关键时段加速
3. **售罄时官方候补更靠谱** —— 候补是服务端排队兑现，不受你的网络和刷新手速影响。脚本盯退票、候补兜底，两条腿走

## 项目结构

```
12306-monitor/
├── run.py                     命令行入口（serve / doctor / stations / burst）
├── config.example.json        配置样例（复制成 config.json 再改）
├── core/
│   ├── config.py              读配置、校验（站名纠错、预售期提醒）
│   ├── engine.py              派任务、收结果、判命中、发通知
│   ├── criteria.py            命中判定逻辑
│   ├── models.py              车次、余票文本解析
│   ├── store.py               SQLite：告警记录、去重
│   ├── notify.py              桌面弹窗 / Webhook / 邮件
│   ├── server.py              本地接口 + 看板推送
│   └── stations.py            车站字典（3407 个站）
├── data/stations.json         车站字典数据
├── static/index.html          看板页面
├── userscript/                浏览器脚本（核心在它）
└── tests/                     测试
```

**为什么查询放在浏览器里？** 因为 12306 的余票接口返回的是加密数据，纯 HTTP 客户端拿到的是密文。要解析就得逆向它的前端加密——那种做法一改版就废，而且属于绕过技术保护措施。所以让浏览器用页面自己的流程解密和渲染，脚本只读渲染后的表格。这既省事也不违规。

## 它是怎么来的

思路来自 [infomation_monitor_platform](https://github.com/ThunderingII/infomation_monitor_platform)：「把请求动作 + 条件判定 + 通知抽象成配置」。但 12306 的查询没法用"一条 HTTP 请求 + 解析 JSON"表达（接口加密、需要登录态、有反爬），所以把"执行"下沉到浏览器，服务端退化成调度器。

好处是 12306 改版时只需要调 `userscript/`，服务端逻辑不用动。
